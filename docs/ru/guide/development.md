# Разработка проекта

## Структура репозитория

Station использует .NET 10. Проекты разделяют контракты, загрузку конфигурации, выполнение, восстановление плагинов и встроенные модули:

| Проект | Ответственность |
| --- | --- |
| `Station.Abstractions` | Контракты модулей, переменных, файлов и запуска процессов. |
| `Station.Configuration.Abstractions` | Контракты документов конфигурации и значений. |
| `Station.Configuration.Yaml` | Загрузка YAML и подстановка Scriban. |
| `Station.Configuration.JavaScript` | Загрузка переменных и ролей через Jint. |
| `Station.Core` | Обнаружение, связывание, планирование и выполнение задач. |
| `Station.Plugins.Abstractions` | Контракты требований и манифестов плагинов. |
| `Station.Plugins` | Восстановление через отдельных поставщиков и кеширование. |
| `Station.Utilities` | Общие средства запуска процессов и проверки прав. |
| `Station.Modules.*` | Встроенные модули. |
| `Station.Cli` | Точка входа CLI и вывод. |

Модель задачи похожа на Ansible: необязательное имя, один ключ модуля и вложенный объект параметров. YAML — формат сериализации; источником истины служит модель объектов .NET в памяти.

## Внедрение зависимостей

`Station.Cli` регистрирует сервисы через `StationServices.AddStation`, создаёт и освобождает контейнер в `Program.cs`. Сервисы Core и плагинов получают зависимости через конструкторы. `AddStationCore` и `AddStationPlugins` регистрируют внутренние сервисы своих проектов.

Загрузчики конфигурации, провайдеры плагинов, шаблонизатор, средство запуска процессов, проверка прав, HTTP-клиент и источник времени используются совместно. Для каждой задачи `ActivatorUtilities` создаёт отдельный модуль с новым `ModuleContext`, получая остальные зависимости конструктора из DI. Интеграционные тесты используют регистрации CLI и могут подменять отдельные зависимости перед созданием контейнера.

`IProcessRunner`, `ProcessCommand` и `ProcessResult` находятся в `Station.Abstractions.Processes`. Реализация остаётся в `Station.Utilities.Processes.ProcessRunner`. Модули `script`, `apt`, `scoop` и `winget` получают `IProcessRunner` через конструктор, сохраняя зависимость проектов только от Abstractions. Коду, который импортировал контракты процессов из Utilities, нужно обновить пространство имён; при прямом создании этих модулей нужно передать исполнитель процессов.

## Выполнение и отмена

`ConfigEngine` передаёт запрошенную отмену вызывающему коду как `OperationCanceledException`. Отмена проверяется до загрузки конфигурации и между этапами задачи. Модуль должен передавать токен асинхронным операциям и позволять отмене распространяться. Если модуль вернулся после отмены, следующий этап или задача не запускается.

Общий исполнитель отклоняет уже отменённый запрос до запуска команды. При отмене работающей команды он запрашивает завершение дерева процессов, ждёт выхода родительского процесса и завершения чтения перенаправленного вывода. Модуль `script` удаляет временный файл запроса при освобождении ресурсов. Это проверяется интеграционными тестами с настоящими PowerShell-процессами, включая родителя и потомка.

Очистка процессов следует [контракту `Process.Kill(entireProcessTree: true)`](https://learn.microsoft.com/dotnet/api/system.diagnostics.process.kill): завершение потомков зависит от прав ОС, а ожидание родителя само по себе не подтверждает выход всех потомков. Интеграционный тест отдельно ожидает завершения своего дочернего процесса.

## Курс развития

Ближайшие этапы направлены на надёжное изменение рабочей станции и автоматизацию:

1. **Надёжность выполнения — реализовано.** Останавливать `check/apply` при ошибках задач, сохранять диагностики и записи выполненных задач, передавать отмену и использовать общий запуск процессов во встроенных модулях и восстановлении плагинов.
2. **Контракты пакетов и скриптов — реализовано.** Пакетные модули отклоняют неверные состояния и ошибки запросов, проверяют точное имя, область установки и установленную версию. Проверяются типы ответа скрипта и повторяющиеся поля JSON. Контракты покрыты регрессионными тестами, идемпотентность — контролируемыми командами. Дополнительно выполнены проверки без изменения пакетов на установленных Scoop, WinGet и WSL/dpkg.
3. **Вывод для автоматизации — реализовано.** Все команды поддерживают `--output json` со схемой версии 1, явными статусами задач, структурированными выходными данными модулей, диагностикой и кодами завершения. Ход работы и управляемый консольный вывод модулей направляются в stderr. Тесты запускают CLI в отдельном процессе и проверяют успех и ошибки; тесты приложения покрывают отмену и восстановление потоков вывода.
4. **Целостность записи файлов — реализовано.** `copy` и `template` подготавливают полное содержимое и заменяют существующие файлы, резервируют имена копий без перезаписи прошлых версий, сохраняют права доступа и следуют символическим ссылкам на файлы. Проверки на настоящих файловых системах Windows и Linux покрывают открытых читателей, блокировки Windows, отмену, совпадения имён копий, отсутствующие цели ссылок и права Unix.
5. **Изоляция кроссплатформенных тестов — реализовано.** Командные фикстуры используют запуск, подходящий для Windows и Linux. Тесты пакетных менеджеров изолируют `PATH`, добавляют разрешённый запуск рантайма .NET, если он нужен PowerShell, и подменяют установку, удаление и запросы контролируемыми командами. Полные наборы тестов выполняются локально на Windows и Linux; в CI настроены Windows и Ubuntu с отдельными артефактами. Платформенные проверки явно отмечают пропуски.

Для замены используется [`File.Replace`](https://learn.microsoft.com/dotnet/api/system.io.file.replace) с временным путём восстановления на том же томе. При ошибке Windows `ERROR_UNABLE_TO_MOVE_REPLACEMENT_2` Station пытается вернуть исходный путь и сохраняет файл восстановления, если это тоже не удалось. Эта ветка следует [документированному контракту ошибок Windows](https://learn.microsoft.com/windows/win32/api/winbase/nf-winbase-replacefilew); автоматические тесты проверяют обычные блокировки и отмену, без искусственного воспроизведения этой редкой ошибки ОС.

## Архитектура вывода CLI

`Program.cs` создаёт контейнер и вызывает `StationCommandLine`. Регистрация команд, проверка общих параметров и обработка вызова находятся в `Station.Cli/Commands`. `StationConsole` и `JsonCommandOutput` реализуют `ICommandOutput` для текстового и JSON-вывода.

JSON-запись преобразует результаты движка в явный контракт с версией и буферизует полный документ до записи в stdout. Внутренние манифесты плагинов и другие детали движка не сериализуются. CLI обрабатывает один вызов на процесс и временно направляет управляемые консольные записи в stderr для JSON-команд, восстанавливая оба потока при завершении, ошибке и отмене. Публичный формат описан в [справке CLI](./cli.md#json-результаты).

## Сборка и тесты

Для тестов нужны .NET 10, Git и PowerShell 7 (`pwsh`) в `PATH`. Из корня репозитория:

```powershell
dotnet build Station.slnx -v minimal
dotnet test --project tests/Station.UnitTests/Station.UnitTests.csproj -v minimal
dotnet test --project tests/Station.IntegrationTests/Station.IntegrationTests.csproj -v minimal
```

Выполняйте сборку и тесты последовательно: проекты разделяют выходные каталоги и состояние восстановления пакетов. В репозитории выбран [Microsoft.Testing.Platform](https://learn.microsoft.com/dotnet/core/tools/dotnet-test-mtp), поэтому в примерах используется `dotnet test --project`. Интеграционные тесты используют временные каталоги и локальные фикстуры; реальные пакетные менеджеры на компьютере не нужны.

Командные фикстуры создают `.cmd` в Windows и исполняемые shell-скрипты в Linux, вызывая PowerShell по заранее найденному абсолютному пути. Тесты пакетов заменяют унаследованный `PATH` каталогом фикстуры; для Linux в нём находятся контролируемые `apt-get`, `dpkg-query` и `sudo`. Процессные тесты WinGet выполняются в Windows: коды завершения Unix не вмещают его HRESULT. Тесты контрактов результатов WinGet выполняются на обеих платформах.

Если PowerShell отсутствует, [официальный способ установки через .NET tool](https://learn.microsoft.com/powershell/scripting/install/alternate-install-methods#install-as-a-net-global-tool) позволяет оставить его внутри рабочей копии. В Linux shell:

```bash
dotnet tool install PowerShell --tool-path ./artifacts/tools
export PATH="$PWD/artifacts/tools:$PATH"
```

При общей рабочей копии Windows и WSL используйте отдельные каталоги результатов Linux:

```bash
dotnet build Station.slnx -c Release --artifacts-path "$PWD/artifacts/linux-check"
dotnet test --root-directory artifacts/linux-check/bin/Station.UnitTests/release \
  --test-modules Station.UnitTests.dll
dotnet test --root-directory artifacts/linux-check/bin/Station.IntegrationTests/release \
  --test-modules Station.IntegrationTests.dll
```

`--test-modules` принимает шаблон относительно `--root-directory`. Задания CI для Windows и Ubuntu используют обычные команды с `--project` и публикуют отдельные артефакты тестов.

Проверка CLI:

```powershell
dotnet src/Station.Cli/bin/Debug/net10.0/Station.Cli.dll --help
dotnet src/Station.Cli/bin/Debug/net10.0/Station.Cli.dll explain --config examples/workstation
```

## Публикация

Сборка автономного исполняемого файла для Windows:

```powershell
dotnet publish src/Station.Cli/Station.Cli.csproj `
  -c Release `
  -r win-x64 `
  --self-contained true `
  -p:PublishSingleFile=true `
  -p:UseAppHost=true
```

Результат — `Station.Cli.exe` в каталоге `src/Station.Cli/bin/Release/net10.0/win-x64/publish/`.

## Сайт документации

Сайт использует VitePress. Установите Node.js и npm, затем из корня репозитория:

```powershell
npm ci
npm run docs:dev
```

Сборка для публикации и локальный просмотр:

```powershell
npm run docs:build
npm run docs:preview
```

Английские страницы находятся в `docs/guide/`, соответствующие русские — в `docs/ru/guide/`. Навигация и локальный поиск настроены в `docs/.vitepress/config.mts`. При изменении описания поведения обновляйте обе версии.
