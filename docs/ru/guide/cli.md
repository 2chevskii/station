# Командная строка

Ниже `station` — условное обозначение CLI. Опубликованный файл Windows называется `Station.Cli.exe`; при разработке из корня репозитория используйте `dotnet src/Station.Cli/bin/Debug/net10.0/Station.Cli.dll`.

```text
station restore       --config <каталог> [параметры]
station explain       --config <каталог> [параметры]
station list roles    --config <каталог> [параметры]
station list modules  --config <каталог> [параметры]
station validate      --config <каталог> [параметры]
station check         --config <каталог> [параметры]
station apply         --config <каталог> [параметры]
```

| Команда | Действие |
| --- | --- |
| `restore` | Разрешает заявленные плагины и показывает их источники и расположение. |
| `explain` | Показывает статическое дерево задач, связанные параметры и видимые переменные. |
| `list roles` | Показывает доступные роли, описания и источники. |
| `list modules` | Показывает доступные модули, описания и источники. |
| `validate` | Восстанавливает плагины, разрешает задачи, связывает параметры и вызывает проверку модулей. |
| `check` | Проверяет и запускает каждую задачу в режиме оценки изменений. |
| `apply` | Проверяет и выполняет каждую задачу по порядку. |

Все команды принимают параметры:

| Параметр | Значение |
| --- | --- |
| `--config <каталог>` | Корень конфигурации; по умолчанию текущий каталог. |
| `--set key=value` | Переопределить переменную. Можно повторять; последнее значение ключа имеет приоритет. Для вложенных ключей используйте точки, например `--set git.user=Alex`. Значения передаются как строки, включая пустое значение и пробелы внутри кавычек. |
| `--plugin-cache-dir <путь>` | Переопределить корень кеша плагинов. Относительные пути отсчитываются от корня конфигурации. |
| `--output text\|json` | Формат результата, по умолчанию `text`. JSON записывается в stdout, сообщения о ходе работы — в stderr. |

Параметры могут находиться перед командой или после неё. `--config`, `--plugin-cache-dir` и `--output` можно указать по одному разу. После каждого `--set` нужен хотя бы один аргумент `key=value`.

Справку по команде выводит `station <команда> --help`. Код завершения при успехе — `0`, при ошибке — `1`, при корректно обработанной отмене — `130`. Успешный `check` возвращает `0` и при наличии ожидаемых изменений.

## JSON-результаты

Все семь команд поддерживают `--output json`:

```powershell
station check --config ./workstation --output json > check.json
station --output json list modules --config ./workstation
```

Завершённый вызов записывает один JSON-документ в stdout, включая ошибки конфигурации, задач и плагинов. Сообщения о ходе работы идут в stderr. Записи модулей через управляемые `Console.Out` и `Console.Error` во время выполнения тоже направляются в stderr. Собственным модулям следует использовать эти средства для диагностики; нативный код, который их обходит, должен оставлять stdout для результата Station.

Общая структура документа:

| Поле | Значение |
| --- | --- |
| `schemaVersion` | Целое число `1`. Несовместимое изменение формата требует новой версии; читатель должен допускать дополнительные поля. |
| `command` | Разрешённая команда, например `check`, `restore` или `list modules`. Для неверного вызова корневой команды используется `station`. |
| `succeeded` | Успешно ли завершилась операция. |
| `exitCode` | Тот же числовой результат, который возвращает процесс: `0`, `1` или `130`. |
| `message` | Краткое описание результата для человека. |
| `diagnostics` | Массив строк диагностики, включая предупреждения успешного запуска. |
| `data` | Объект данных команды; null при ошибках аргументов, отмене и неожиданных ошибках вызова. |

Содержимое `data` зависит от команды:

| Команда | Данные |
| --- | --- |
| `validate`, `check`, `apply` | `summary` с `taskCount`, `changedCount`, `failedCount`, `skippedCount` и массив `tasks` в порядке выполнения. |
| `restore` | `plugins` с полями `requirement`, `pluginName`, `version`, `pluginRoot`, `cacheHit`, `isLocal`. Успешно восстановленные плагины сохраняются в результате при ошибке другого требования. |
| `list roles`, `list modules` | `components` с полями `name`, допускающим null `description` и `source`. |
| `explain` | Допускающий null `plan` с полями `text`, `kind` и рекурсивными `children`. Виды узлов: `root`, `section`, `task`, `detail`, `value`, `error`. |

Каждая запись задачи содержит `taskName`, `moduleName`, допускающий null `roleName`, `status`, `changed`, `failed`, `skipped`, допускающий null `message` и объект `outputs`, который тоже может быть null. Статус выбирается в порядке приоритета: `failed`, `changed`, `skipped`, `ok`. Отдельные флаги сохраняют частичный результат: у неуспешной задачи может быть `changed: true`.

Записи задач и счётчики описывают попытки выполнения. `validate` возвращает пустой массив `tasks`, поскольку только проверяет задачи. Ошибки разрешения, связывания параметров и проверки попадают в диагностику без записи выполнения. Ранее выполненные задачи сохраняются в результате при последующей ошибке. Отмена возвращает `data: null`; уже внесённые изменения сохраняются, а принудительное завершение процесса может помешать записи результата.

Ошибки аргументов возвращаются в JSON, когда доступен корректный выбор `--output json`. Неверное значение самого формата использует обычный вывод ошибок парсера. `--help` и `--version` сохраняют текстовый вывод.

## Рекомендуемый порядок

```powershell
station list modules --config ./workstation
station explain --config ./workstation
station validate --config ./workstation
station check --config ./workstation
station apply --config ./workstation
```

`explain` и команды инвентаризации могут восстанавливать плагины для обнаружения их экспортов. `validate`, `check` и `apply` тоже делают это автоматически. `check` вызывает каждый модуль в режиме проверки; собственный модуль должен сам учитывать этот режим.

`validate` собирает ошибки задач и продолжает проверять остальные задачи без выполнения. `check` и `apply` останавливаются при первой ошибке разрешения модуля, связывания параметров, проверки, прав или выполнения. Задача с ошибкой проверки не выполняется. Результат сохраняет предупреждения и записи предыдущих задач. Уже внесённые `apply` изменения сохраняются: выполнение последовательное, без отката.
